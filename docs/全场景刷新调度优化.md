# 全场景刷新调度优化

## 原因与实现

完整场景读取后原先额外等待 2 秒；对象列表又早于碰撞体读取生成，导致发布时动物可能已经消失。

- 完整场景目标起始间隔改为 0.2 秒，扣除本轮读取耗时，最低保留 0.05 秒空闲。目标不是保证实际 5 Hz；阈值为工程预算。
- 空闲、错误保留 2 秒重试退避；停止和刷新事件仍可唤醒等待。关闭线程等待预算独立于刷新周期。
- 发布前重新遍历活跃实体表，移除消失对象；昆虫、鸟、动物及每日特殊资源重新验证归属、类别和位置。
- 再次检查角色归属及场景根，防止跨场景混用。真实碰撞数据、导航隔离、固定资源历史缓存均保留。
- 本轮保留工作区原有 20 Hz UI 刷新修改，不将其作为本轮提交内容。

## 验证

新增测试先获得 4 失败、1 通过，修复后增加固定对象和局部读取失败场景，共 7 项通过。
完整默认测试：2423 通过、27 预期失败，另 2 个 subtest 通过，零失败，164.52 秒。
冻结包相关测试：326 通过；89 个模块代码与候选源码一致。
修改模块 pyflakes 和 git diff --check 通过。

只读同进程场景计时（含其他测试/构建并发，非受控性能基准）：旧暖读 0.861/0.882 秒，新暖读 0.923/0.925 秒；约 3367–3369 对象和 4226 碰撞体。新晚期核对有额外成本，调度预计从约 2.9 秒缩短至约 0.97 秒。冷读旧 1.256 秒、新 1.239 秒，不能据此声称冷读优化。
未自动移动角色，未执行真实昆虫捕获测试。每轮扫描更密集会增加后台 CPU 使用；大型场景实际频率仍受完整读取耗时限制。

本地验证证据：work/native-monitor/scene-refresh-20261025-215029（不提交运行数据）。
