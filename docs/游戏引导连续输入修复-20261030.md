# 游戏引导连续输入修复

## 复现与范围

用户反馈为连续的短促停顿，像点按行走键。旧实现的到期引导核对先释放按键，
收到不同快照对象时也先释放，尚未判断几何是否改变。
新增的两项离线短直路测试在修改前均失败：同方向分别重复按下前进键 8 次，
预期为开始时按下一次、结束时释放。

本次只改游戏引导跟随。普通采集回放、保存路线、到达半径和水域边距保持原行为。
岸侧临时引导点与原碰撞规划器继续使用。

## 输入许可与独立监控

正常引导心跳不再例行松键。相同几何的新快照先由原刷新与签名逻辑核对，
实际重建碰撞图、路径搜索和引导路线版本变化仍在必要工作前释放输入。

仅在当前坐标、方向、引导健康状态与局部通路完成检查后，允许更新移动许可。
许可截止时间取以下最早值：

- 最新位置采样后 0.15 秒；
- 现有引导健康时间戳加原有有效期；
- 最早托管/原生碰撞观测时间加原有碰撞有效期；
- 按当前局部目标距离与现有速度估计计算的短行走预算。

0.15 秒和 0.01 秒监控轮询为工程预算，不是实测游戏能力或实时系统时延保证。
实际线程调度和 Windows 输入调用仍存在延迟，不宣称硬实时停止。
开始读取、读取未完成或后台监控都不能续期。

独立守护线程不读取游戏内存、不规划、不按下按键，只检查短许可、停止/暂停状态、
窗口焦点与尺寸。超时或状态失效时释放按键。输入修改与监控释放共用互斥锁，
控制器处理撤销后必须重新核对，不得沿用已释放的按键集合。
输入释放失败显式上报；退出时停止监控并释放输入。原有脱困操作保持原保护流程。

## 时钟与失效

碰撞工作线程使用 `time.monotonic`，Windows Python 3.12 的控制时钟为
`perf_counter`，不能直接比较原始时间戳。本机确实存在原点差异。
`GuidanceNavigator.collision_deadline()` 在来源时钟中计算剩余时长，再转换为控制时钟截止时间。
不延长碰撞 TTL。注入不同来源时钟的测试须显式传入 `scene_clock`。
无质量字段的旧测试快照保持原兼容约定，不代表生产数据可缺少质量校验。

## 诊断与验证边界

行走状态记录 `input_continuity`，包含有界的最近释放原因、计数和剩余许可。
包括正常规划/碰撞图重建、路线变化、数据失效、许可过期、停止、失焦和清理等原因；
后台监控不直接写 UI 或回放日志，由主线程发布诊断。

测试覆盖正常心跳、同几何新快照、读取阻塞时独立释放、F9、暂停、失焦、查询异常、
新墙体、真实目标/场景切换、碰撞 TTL 上限、不同计时原点、过期碰撞、设备释放失败、
撤销后同步按键集合与监控线程清理。所有输入均为假设备，未自动操作真实游戏。

离线通过不能证明实机行走已连续。更新后需人工在普通直路上启动跟随，
核对短促停顿、释放原因计数、停止/失焦保护，再分别测试真实障碍及区域流式加载。
碰撞数据供应空档仍会要求停止，不以删除安全保护来改善表观连续性。
