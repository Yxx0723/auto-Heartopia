# 自动烹饪需求与实施方案

日期：2026-10-24

项目：Yxx0723/auto-Heartopia

审阅基线：`restore/d50087c-20261023` / `8d89549`

状态：需求草案，供审阅；尚未实现或实机验证自动烹饪。

## 一、目标与推荐范围

自动完成指定料理的连续制作，处理翻炒提示、收取成品，并通过随身背包增量确认结果。每一锅保留完整状态，避免点击没有生效、收取延迟或暂停恢复后重复投料。

推荐路线：先完成单灶台，再增加自动选菜，最后考虑多灶台。以下首版范围是本次方案建议，不代表已完成开发或用户已逐项确认。

### 首版包含

1. 人物由用户手动移到灶台前，打开选菜界面并选好一种食谱；程序启动前仍未点击开始制作。
2. 程序核对食谱、投料界面和材料，启动一锅，识别翻炒提示，完成收菜。
3. 同一种料理连续制作，可设置目标成功锅数和材料保留数量。
4. 成品数量实际增加后才确认成功；失败产物和未确认结果分别记录。
5. 支持 F6 暂停/继续、F9 停止；与采集回放互斥。
6. 每锅记录操作、状态变化、库存前后数量及异常原因，供后续复盘。

### 首版不包含

- 自动寻路回家、寻找或摆放灶台。
- 多灶台并行、自动购买材料、取用仓库材料。
- 自动解锁食谱、更换为其他料理、使用万能食材或稀有替代材料。
- 自动追求或保证指定成品星级。
- 修改游戏内存、注入、调用内部烹饪函数或改变计时速度。
- 修改已有采集点、路线顺序和走法记忆设置。

## 二、现有能力与缺口

以下结论来自当前仓库源码。已有背包与进食能力不等于已有烹饪能力。

| 能力 | 当前代码 | 可复用部分与限制 |
| --- | --- | --- |
| 随身背包归属及稳定性核对 | `utils/drivers/food_inventory.py` 的 `owned_rows()` | 验证当前场景、所有者、随身背包及读取期间变化；不代表已识别烹饪材料限制 |
| 背包物品总量 | 同文件 `counts_snapshot()`；`coordinate_memory.py` 的 `backpack_counts_snapshot()` | 可用于数量基准与增量确认；包含锁定物品、合并分堆，不能直接用于选择可投放材料 |
| 可食用料理及星级 | `FoodInventoryReader.snapshot()`、`utils/core/food_policy.py` | 现有逻辑服务自动进食；不能直接当作食谱或原料列表 |
| 界面识别 | `utils/vision/food_menu.py`、`utils/vision/matcher.py` | 可参考区域识别、稳定画面核对；尚无经核对的灶台、翻炒和收菜模板 |
| 输入及热键 | `utils/drivers/town_window.py`、`windows_input.py`、`timeline_hotkeys.py` | 复用窗口、输入释放和控制机制；烹饪具体按键、点击位置仍须核对 |
| 回放任务状态 | `utils/ui/point_playback.py` | 有活动线程和启动检查；新增烹饪入口仍需建立双向互斥，不能仅依靠旧入口检查 |
| 全程采集证据 | `utils/core/harvest_evidence.py` | 可参考首次基准、作用域与证据编号；当前类绑定萤石、橡木编号，不直接套用为烹饪记录 |
| 过程归档 | `utils/drivers/playback_history.py` | 可复用日志写入方式和去重思路；烹饪应单独使用日志结构，不混入导航走法学习 |

当前没有经源码和实机共同确认的灶台归属、烹饪阶段、翻炒期限、原生完成事件或完整食谱读取接口。首版以画面识别操作、只读库存核对结果。后续找到可靠的只读字段后，再作为辅助来源接入。

## 三、交互与配置

推荐增加独立的“自动烹饪”区域，避免让采集回放承担两种不同任务。

| 项目 | 建议行为 |
| --- | --- |
| 当前料理 | 用户在游戏中选择，工具显示核对到的名称；名称或身份不明确时不开始 |
| 目标成功锅数 | 用户设置；按确认成功的锅计数，不按开始按钮或翻炒次数计数 |
| 材料保留量 | 可设置各材料最低余量；未知实际配方用量时不能估算剩余可做锅数 |
| 启动 | 工具完成检查后等待用户切回游戏按 F6，避免点击工具时向游戏发出操作 |
| 暂停/继续 | F6；暂停释放输入，继续前重新识别当前锅 |
| 停止 | F9；立即结束自动输入并保存记录，不自动取消游戏内正在制作的料理 |
| 状态 | 显示当前料理、当前阶段、成功/失败/待确认锅数及具体异常原因 |

首版不提供无上限自动重投。目标达成、材料不足、无法确认正在制作的内容或存在未解决的收取结果时，不开启下一锅。

## 四、每锅状态与操作流程

### 4.1 状态定义

| 状态 | 输入条件 | 允许操作 | 转移依据 |
| --- | --- | --- | --- |
| 等待启动 | 游戏、灶台、食谱和尺寸已确认 | 等待 F6 | 用户启动 |
| 检查投料 | 选菜界面与目标食谱一致 | 核对材料，取得库存基准 | 材料、归属和开始按钮均明确 |
| 等待开锅确认 | 已发送一次开始操作 | 观察，不重复投料 | 出现已进入烹饪的可靠画面 |
| 烹饪中 | 已确认当前锅正在制作 | 观察翻炒及完成提示 | 提示出现或画面状态变化 |
| 响应翻炒 | 明确识别当前操作提示 | 响应一次，等待提示变化 | 提示消失、重新出现或阶段明确变化 |
| 等待收取 | 明确识别完成状态 | 点击一次已确认的收取目标 | 收取状态变化 |
| 核对产出 | 收取已尝试或发生明显完成变化 | 持续核对库存，不开新锅 | 成品增量、失败产物、超时或归属变化 |
| 本锅成功 | 证据满足确认规则 | 累计成功数，检查是否继续 | 下一锅或任务完成 |
| 本锅失败 | 经核对出现失败状态或失败产物 | 保存原因，检查是否允许继续 | 材料和界面重新明确 |
| 结果待确认 | 数据不足，不能归入成功或失败 | 有界复核，必要时等待人工处理 | 证据补齐或用户停止 |

“未确认”不是失败，也不是没有产出。菜单消失不代表开锅成功，翻炒图标消失不代表料理完成，点击收菜不代表成品已入包。

### 4.2 首次开锅

1. 检查没有采集回放或其他自动输入任务在运行。
2. 检查当前游戏窗口、客户区尺寸及已识别的选菜界面。
3. 核对目标食谱及实际材料；不能只看菜名相似或默认选中位置。
4. 读取首次稳定的随身背包快照，创建本锅唯一编号。
5. 确认可投放材料和保留量后，发送一次开始操作。
6. 等待进入制作状态；若画面不明确，保留本次操作为待确认，不盲目再次投料。

如果用户启动时已经有一锅正在制作，首版不直接接管并声称能核对产出。应提示先完成当前锅，再从未开始投料的选菜界面启动；后续版本可单独设计无初始基准的接管模式。

### 4.3 翻炒与提示去重

- 根据实时提示决定操作，时间只作观察窗口和超时辅助，不把固定秒数当作烹饪阶段的证明。
- 用已确认的窗口锚点定位相关区域，不能只靠屏幕绝对坐标。
- 使用短时间连续观测核对提示稳定性；帧数和间隔须根据真实响应窗口校准，不能因等待识别而错过操作。
- 同一个提示只响应一次。只有确认提示重新出现或进入下一阶段后，才允许再次响应。
- 提示残留、点击后没有变化、同一画面重复出现时，先重新识别，不能默认连续双击或无限连点。
- 具体操作是点击图标、按钮还是按键，必须依据当前客户端实际画面确认。

### 4.4 收菜与下一锅

先识别完成状态，再发送收取操作。成品未确认入包前，不重新选菜投料，也不自动食用可能作为本锅产出的料理。确认一锅后重新读取库存及材料，不直接递减旧库存推算下一锅。

## 五、材料与产出确认

### 5.1 材料选择

- 首版材料来源仅限当前角色随身背包。
- 锁定、禁用及用户保留的材料不参与投料。
- 原料星级、替代关系、配方用量需要分别核对；现有背包总量接口没有提供这些投料保证。
- 不自动使用万能食材、稀有材料或价值更高的替代物。
- 游戏自动填料后，也必须核对实际选中的材料；不能假设默认填料符合保留规则。
- 无法可靠区分同名材料的星级、锁定份数或分堆身份时，先停止开启新锅，给出具体原因。
- 如果游戏当前界面不能避免自动消耗受保护材料，该食谱暂不支持自动开锅。

### 5.2 每锅证据

建议保存以下字段，运行数据仅留本机：

| 字段 | 用途 |
| --- | --- |
| 任务编号、锅编号 | 区分任务和去重 |
| 游戏场景/角色/背包作用域 | 防止跨归属比较 |
| 灶台观测标识及来源 | 绑定当前画面；不把临时地址当作跨重启稳定身份 |
| 食谱身份、名称、确认来源 | 避免选错同名或变体料理 |
| 预期产物编号集合 | 明确哪些库存增加可算目标产出；不得凭名称猜编号 |
| 材料及成品首次库存 | 在开始投料前取得；首次输入后不得补建基准冒充制作前库存 |
| 阶段、操作编号和时间 | 保存开始、翻炒、收取以及暂停恢复经过 |
| 最新库存、确认时库存及增量 | 兼顾延迟变化和已确认事实的保留 |
| 确认状态、来源与原因 | 区分确认成功、确认失败、未知及证据失效 |

### 5.3 确认规则

1. 同一锅的首次基准覆盖整个制作和收取过程，不因阶段变化、短时读不到或暂停而覆盖。
2. 按已核对的产物编号聚合各分堆；如果同名料理各星级共用编号，则数量确认与星级统计分开处理。
3. 同一作用域内，观察到目标产物正增量，并与当前锅的制作/收取阶段相符，才标记确认成功。
4. 材料减少只能辅助证明发生消耗，不能证明做出目标料理；也不要求每锅材料必须减少，免耗材等实际机制仍待核对。
5. 失败产物需要先核对编号与归属，不凭图标近似或未知物品增加推断失败。
6. 归属变化、对象替换或进程重启使未完成证据失效；旧记录保留，但不能与新作用域累计确认。
7. 同一锅被多次观察到成功，只计一次；已确认增量保留确认时快照，不被后续消费或安静读数抹掉。
8. 读不到不是零，超时不是没有产出。所有等待和重试均须有上限；具体时限在实机采样后确定，不照搬萤石、橡木的延迟参数。

背包正增量证明数量增加，不能单独证明唯一来源。首版串行烹饪并排除自动进食、交易、取仓等工具动作；若用户手工取得或移走同名料理，当前锅结果可能仍需人工核对。

## 六、暂停、异常及恢复

| 情况 | 必须行为 |
| --- | --- |
| 切出游戏或窗口失焦 | 立即释放输入，进入暂停；不能向其他窗口点击 |
| F6 暂停 | 保留当前锅和首次基准，停止输入；明确游戏内锅的计时可能继续 |
| F6 继续 | 重新核对窗口、界面和当前阶段；不能从旧倒计时继续盲点 |
| F9 停止 | 释放所有输入并落盘；保留未完成记录，不自动取消游戏中的制作 |
| 分辨率或 UI 比例变化 | 旧定位失效，重新定位并确认；失败则暂停，不使用旧坐标 |
| 开始按钮点击无反馈 | 保留“开始待确认”，不立即再投一份材料 |
| 翻炒提示点击后仍显示 | 核对是否同一次提示、输入是否生效，不自动认定进入下一阶段 |
| 成品延迟入包 | 保持待确认，有界复核；不开下一锅，不重复增加成功计数 |
| 背包读取暂时失败 | 释放当前不必要输入并等待重读；不归零、不降级为材料耗尽 |
| 背包满或收取失败 | 停止新开锅，显示原因；未经确认不自动丢弃、出售或发邮箱 |
| 材料不足 | 停止新开锅并显示缺失材料；不买材料、不自动换菜 |
| 背包或场景归属变化 | 使未完成比较失效，停止任务并要求重新核对 |
| 体力不足 | 只在不会错过当前烹饪操作且本锅结果已解决的安全边界进食；无法确认时不插入背包操作 |
| 程序重启 | 显示上次未完成记录，不自动恢复按键或补投料 |

恢复应围绕实际状态进行。识别失败可以重试观察，已经可能产生材料消耗的操作不能直接无限重试。

## 七、技术接入建议

采用增量接入，不改写现有寻路器，不将烹饪逻辑塞进坐标跟随循环。下面均为拟新增文件，并非现有能力。

| 模块 | 拟新增位置 | 职责 |
| --- | --- | --- |
| 状态与策略 | `utils/core/cooking.py` | 纯状态转移、操作去重、材料保留策略；不调用输入或截图 |
| 每锅证据 | `utils/core/cooking_evidence.py` | 任意经核对的料理产物集合、作用域、首次基准和结果去重 |
| 烹饪界面识别 | `utils/vision/cooking_menu.py` | 窗口锚点、选菜、翻炒、完成及异常提示 |
| 执行流程 | `utils/flows/cooking.py` | 状态调度、截图/库存/输入适配、暂停停止和收尾 |
| 窗口任务控制 | `utils/ui/cooking_control.py` | 独立任务线程、状态队列、配置和双向互斥 |

优先复用只读背包、窗口、输入、热键和日志工具。不要让 `core` 直接导入截图、系统输入或 `vision`，新增接口遵守现有架构测试约束。

输入权由一个任务持有：启动烹饪时检查回放，启动回放时也检查烹饪。维修、进食、回放和烹饪不能同时发送输入；烹饪中的危险时段不得插入维护菜单。退出或异常时在 `finally` 中释放输入并归还任务所有权。

## 八、性能和记录

- 识别只截取已确认的目标区域；界面切换后刷新定位。
- 模板、识别特征可缓存，但窗口尺寸、比例或模板版本变化后必须失效。
- 翻炒时机检查、库存读取、日志落盘分开调度，不能每帧全量读背包或同步写大图。
- UI 主线程只更新状态；后台识别结果带采集时间和窗口版本，过时结果不能触发点击。
- 目标识别、库存读取和输入调度的实际耗时需分别测量；当前背包单项测量不能代表整个烹饪循环性能。
- 图像识别、等待和重试使用单调时钟，并在可中断的小步中检查暂停、停止及窗口归属。
- 建议本地归档到独立的“烹饪记录”目录，保存任务摘要、每锅证据及事件；截图仅保留必要诊断画面并设置容量上限。
- 烹饪记录不参与导航走法学习；日志、诊断截图、背包快照和个人配置不上传 GitHub。

## 九、分阶段实施与验收

### 阶段 A：只读核对和界面采样

先确认一口灶台、一种食谱的选菜、实际材料、开始、翻炒、完成、收取和背包变化。核对客户端版本、分辨率和 UI 比例，记录输入方式与提示窗口。

验收：能够区分关键状态和未知状态；确认产物编号与首次库存来源；明确哪些字段只能依靠画面。此阶段不以离线图片识别代替真实烹饪验证。

### 阶段 B：单锅流程

先写离线测试，再实现单锅状态和执行。首次实机验证限定一锅，由用户确认已选食谱和材料后再进行。

验收：没有重复投料或收取；翻炒提示正确去重；通过背包增量确认结果；暂停、停止、失焦及异常均释放输入。

### 阶段 C：单灶连续制作

增加目标锅数、材料保留、每锅重读、延迟确认及任务汇总。

建议实机验收样本：同一已核对食谱连续至少20锅，另覆盖材料不足、背包满、暂停恢复和延迟入包。20锅是拟定的验收样本量，不是已完成结果或成功率承诺；异常场景可在不实际损失物品的条件下分开验证。

验收：记录能逐锅对应实际产出；成功、失败、待确认总数与实际过程一致；不存在重复开锅或未知结果自动升级成功。

### 阶段 D：自动选菜及多灶扩展

先自动选择同一食谱，再评估双灶。每个灶台独立保存状态、归属、下一操作期限和产出证据；错开开锅时间，优先处理最紧急提示，再考虑移动成本。

若不能可靠绑定灶台或缺少翻炒期限，不启用多灶并行。多灶、自动回家和跨菜谱轮换均属于后续范围，不因单灶完成而自动开始。

### 必须覆盖的离线测试

1. 提示持续存在、短暂闪烁、重复帧及消失后重新出现。
2. 开始操作有延迟，不能重复消耗材料。
3. 收取后延迟入包，不重复收取、不重建制作前基准。
4. 多星级分堆、同名变体、失败产物与目标产物混淆。
5. 库存未知、数量下降、锁定份数、保留量不足、错误背包归属。
6. F6、F9、失焦、尺寸变化发生在每个关键操作前后。
7. 任务停止后仍有旧识别结果返回，不能触发后续点击。
8. 场景、角色、灶台对象或进程变化后，旧证据不能确认新锅。
9. 回放和烹饪双向互斥，维护流程不抢占烹饪输入。
10. 日志写入失败、重复确认及程序重启后存在未完成记录。

每个开发阶段按变更执行专项测试、相关回归、默认测试和适用的冻结包检查。报告分别列出离线结果、只读核对和真实游戏结果，不混写为“实机通过”。

## 十、尚待实机核对的问题

1. 当前使用哪一种灶台，食谱选定后具体如何开始、翻炒和收取。

3. 提示出现时长、操作反馈时长、一次料理有几次提示及失败后的状态。

5. 是否会出现免耗材、多份产出、背包满载转存等影响库存判断的机制。
6. 当前食谱的成品、星级和失败产物在背包中的实际编号与组织方式。
