# auto-Heartopia 单灶自动烹饪系统开发计划书

项目技术方案 · D 方案 · 分阶段实施版 · 2026-11-07

本项目采用 内存只读感知 + 游戏原生输入 + 状态机控制 + 视觉辅助诊断 的混合架构。

核心目标是：玩家手动走到灶台旁，程序自动使用默认食谱完成烹饪，包括游戏随机触发的翻锅事件、收菜、产出确认和连续制作。

## 最终目标流程

玩家手动走到灶台旁

不负责寻找灶台，不负责自动移动

数字键 1 打开灶台

读取默认食谱和材料槽

开始烹饪

记录当前锅次和材料状态

随机翻锅事件监测

游戏触发才翻锅，可能多次，也可能不触发

收菜

识别收菜条件并执行一次

确认成品入包

通过对应料理数量增量确认本锅结果

判断目标锅数

未完成则打开下一锅，完成则结束

## 一、项目目标与范围

### 1. 核心功能

| 功能   | 具体要求                |
| ---- | ------------------- |
| 灶台交互 | 玩家手动靠近，程序发送主键区数字键 1 |
| 默认食谱 | 自动读取并使用当前默认食谱       |
| 材料核对 | 读取实际材料槽及背包数量        |
| 开始烹饪 | 确认材料和食谱后执行          |
| 随机翻锅 | 根据游戏实际事件触发，不自行模拟概率  |
| 收菜   | 识别收菜条件并执行           |
| 产出确认 | 核对本锅对应料理的实际数量增量     |
| 连续制作 | 按目标锅数循环             |
| 暂停恢复 | 保留当前锅次、阶段和操作记录      |
| 安全停止 | F6、F9、失焦保护继续有效      |

### 2. 本期不做

- 自动寻找灶台。
- 自动移动人物或接入寻路。
- 自动选择其他食谱。
- 自动替换材料。
- 多灶台同时烹饪。
- 通过写入游戏内存直接修改烹饪状态。
- 依赖固定屏幕坐标、鼠标点击和固定分辨率。
- 通过固定时间模拟翻锅事件。

首版只支持玩家手动靠近灶台后的单灶、默认食谱自动烹饪。

## 二、技术架构

### 1. 整体架构

A. 游戏状态读取层

只读读取场景、烹饪系统、食谱、材料、背包和烹饪事件。

B. 烹饪状态机

判断当前锅次、烹饪阶段、翻锅需求、收菜条件和异常状态。

C. 输入控制层

发送游戏原生按键、释放按键、输入互斥。

D. 结果验证层

检查游戏状态变化、材料消耗、料理产出。

E. 任务管理和界面层

目标锅数、当前阶段、已确认锅数、错误信息、暂停和停止。

### 2. 各层职责

| 模块                     | 主要职责          |
| ---------------------- | ------------- |
| CookingStateReader     | 读取烹饪系统真实状态    |
| CookingRecipeReader    | 读取默认食谱及材料槽    |
| CookingInventoryReader | 读取材料与成品数量     |
| CookingEventDetector   | 识别开始、翻锅、收菜等事件 |
| CookingStateMachine    | 管理每锅的完整生命周期   |
| CookingInputController | 执行游戏原生输入      |
| CookingResultVerifier  | 确认操作结果        |
| CookingTaskManager     | 管理锅数、暂停和恢复    |
| CookingUI              | 展示运行状态和操作控制   |

优先复用现有代码，不重复实现已经具备的读取能力。

## 三、烹饪状态机设计

这是整个项目最重要的部分。

### 1. 状态定义

| 状态                   | 说明      | 允许的行为     |
| -------------------- | ------- | --------- |
| `IDLE`               | 空闲      | 等待开始      |
| `STOVE_READY`        | 灶台可交互   | 发送数字键 1   |
| `MENU_OPEN`          | 食谱面板打开  | 读取默认食谱    |
| `RECIPE_VALIDATED`   | 食谱与材料确认 | 准备开始      |
| `START_DISPATCHED`   | 开始操作已发送 | 等待反馈      |
| `COOKING`            | 正常烹饪    | 持续读取状态    |
| `FLIP_REQUIRED`      | 游戏要求翻锅  | 准备翻锅      |
| `FLIP_DISPATCHED`    | 翻锅操作已发送 | 等待确认      |
| `HARVEST_REQUIRED`   | 游戏允许收菜  | 执行收菜      |
| `HARVEST_DISPATCHED` | 收菜操作已发送 | 等待确认      |
| `RESULT_VERIFYING`   | 产出确认中   | 检查背包      |
| `POT_COMPLETED`      | 本锅完成    | 更新锅数      |
| `NEXT_POT`           | 准备下一锅   | 重新打开默认食谱  |
| `PAUSED`             | 暂停      | 保存当前进度    |
| `ERROR`              | 异常      | 安全停止并记录原因 |
| `COMPLETED`          | 全部完成    | 释放输入并结束   |

### 2. 随机翻锅机制

重点开发模块

游戏会以不固定概率要求翻锅，因此不能使用固定时间触发。

正确逻辑：

1. 进入 `COOKING`。
2. 持续读取游戏烹饪状态。
3. 判断是否出现翻锅需求。
4. 确认事件身份和有效性。
5. 发送一次翻锅输入。
6. 记录本次翻锅事件。
7. 等待游戏状态发生对应变化。
8. 确认成功后返回 `COOKING`。
9. 继续监测下一次事件，直到出现收菜条件。

需要支持：

- 一锅没有翻锅事件。
- 一锅出现一次翻锅事件。
- 一锅出现多次翻锅事件。
- 翻锅提示持续存在。
- 翻锅后反馈延迟。
- 翻锅读取暂时失败。

关键原则：游戏要求翻锅才执行，不要求就绝不主动翻锅。

还必须区分事件持续存在与新事件产生，避免同一个翻锅事件被重复处理。

如果现有内存读取无法证明翻锅事件已经触发，先完成事件识别研究，不允许直接把某个猜测字段当作可靠信号。

### 3. 收菜机制

当游戏进入可收菜状态：

1. 确认当前锅次。
2. 确认收菜条件。
3. 记录收菜前成品数量。
4. 发送一次收菜操作。
5. 释放输入。
6. 等待烹饪状态退出或变化。
7. 读取背包成品数量。
8. 确认对应料理实际增加。

如果背包读取暂时失败，保留本锅状态，只重试读取，不重复收菜。

## 四、输入方式与交互规则

### 1. 灶台入口

玩家手动走到灶台附近，处于游戏允许交互的距离。

程序不进行灶台定位、人物移动和寻路。

确认游戏窗口及任务互斥后，发送一次键盘主键区数字键 `1`。

- 使用 `VK_1`。
- 不使用 `VK_NUMPAD1`。
- 不使用 Q 键。
- 不使用鼠标坐标点击。

### 2. 后续烹饪输入

开始、翻锅和收菜的实际输入方式，必须分别审查现有代码和历史实机证据。

不能直接假定三种操作使用同一个按键。

每个动作都需要遵循：

`确认条件 → 发送一次输入 → 释放输入 → 读取状态变化 → 确认成功`

不得使用连续按键碰运气。

### 3. 输入安全

- F6：沿用项目现有的任务控制语义。
- F9：立即停止并释放所有输入。
- 游戏失焦：按现有保护策略停止输入。
- 任务互斥：烹饪期间禁止采集、维修、进食等其他自动输入任务并发操作。
- 异常退出：确保按键和鼠标按钮释放。

## 五、食谱与材料管理

首版不提供自动选食谱功能。

### 食谱处理

- 使用游戏当前默认食谱。
- 读取实际食谱身份。
- 不主动切换食谱。
- 不自动修改材料槽。
- 每锅开始前重新核对当前食谱。

### 材料处理

开始前检查：

1. 食谱是否可确认。
2. 材料槽是否完整。
3. 实际填入材料是否符合食谱。
4. 材料是否属于当前背包。
5. 材料是否足够。
6. 材料是否处于允许使用状态。

材料不足时暂停，不自动替换。

### 产出确认

每锅独立记录：

```
pot_id
recipe_id
ingredient_snapshot_before
inventory_before
start_confirmed
flip_event_count
harvest_confirmed
inventory_after
output_delta
pot_result
```

料理数量增加必须与本锅对应的产物绑定。

如果存在其他来源同时增加相同料理，无法可靠归因时，应标记为待确认，而不是直接计算成功。

## 六、异常处理与恢复机制

| 异常      | 处理方式         |
| ------- | ------------ |
| 灶台无法交互  | 等待玩家调整位置     |
| 面板打开失败  | 不重复盲目发送按键    |
| 食谱读取失败  | 有限重试读取       |
| 材料不足    | 暂停任务         |
| 开锅反馈不明确 | 保留待确认状态      |
| 翻锅读取失败  | 保留当前锅次并重试读取  |
| 翻锅执行失败  | 不直接重复输入      |
| 收菜反馈延迟  | 保留收菜待确认状态    |
| 背包读取失败  | 重试读取，不重复收菜   |
| 游戏失焦    | 释放输入         |
| F9      | 立即停止         |
| 程序异常退出  | 释放输入，记录未完成锅次 |

特别要求：任何已经发送但尚未确认的动作，都必须保存为待确认状态。程序重启后不能直接重复执行。

## 八、分阶段开发计划

1. P0：现有代码审计与灶台入口验证

   第一阶段
   - 保护现有代码和未提交修改。
   - 复用食谱、材料、背包读取。
   - 玩家手动靠近灶台。
   - 使用数字键 1 打开灶台。
   - 确认默认食谱面板打开。
   - 确认实际材料槽。
   验收：不开始烹饪，入口稳定通过。
2. P1：单锅完整自动烹饪
   - 开始一锅。
   - 识别烹饪状态。
   - 研究随机翻锅事件。
   - 实现翻锅操作及结果确认。
   - 识别收菜状态。
   - 执行收菜。
   - 确认成品增量。
   验收：完整自动完成一锅，产出可验证。
3. P2：连续三锅测试
   - 完成一锅后自动进入下一锅。
   - 每锅重新核对默认食谱。
   - 每锅独立记录材料与成品。
   - 处理多次翻锅。
   - 测试暂停和恢复。
   - 测试材料不足与背包异常。
   验收：连续三锅全部独立确认。
4. P3：正式页面集成
   - 恢复烹饪页面。
   - 接入现有任务互斥。
   - 接入 F6、F9。
   - 完善日志和异常提示。
   - 完成整体回归。
   验收：作为独立功能稳定运行。

## 九、测试与验收标准

### P0 测试

- 灶台交互条件确认。
- 数字键 1 输入正确。
- 默认食谱识别正确。
- 材料槽读取正确。
- 不重复发送交互输入。
- 原有烹饪专项 66 项测试继续通过。

### P1 测试

| 测试场景        | 预期结果      |
| ----------- | --------- |
| 一锅不触发翻锅     | 正常进入收菜    |
| 一锅触发一次翻锅    | 正确翻锅一次    |
| 一锅触发多次翻锅    | 每次独立处理    |
| 翻锅提示持续存在    | 不重复执行同一事件 |
| 翻锅反馈延迟      | 等待确认      |
| 翻锅状态读取失败    | 保留当前锅次    |
| 收菜成功但背包读取延迟 | 不重复收菜     |
| 成品数量未增加     | 不标记本锅成功   |

### P2 测试

- 连续三锅成功。
- 每锅材料消耗正确。
- 每锅成品数量正确。
- 不漏翻锅。
- 不重复翻锅。
- 不重复开锅。
- 不重复收菜。
- 暂停恢复不丢失进度。

### 正式验收目标

| 指标         | 目标  |
| ---------- | --- |
| 错误开锅       | 0 次 |
| 重复翻锅       | 0 次 |
| 漏处理已确认翻锅事件 | 0 次 |
| 重复收菜       | 0 次 |
| 未确认产出却计为成功 | 0 次 |
| 未授权输入      | 0 次 |
| 连续三锅独立确认   | 3/3 |

所有指标以可验证的实际事件为准，不能用程序发送了按键代替游戏操作成功。

## 十、代码保护与执行规范

1. 开始前检查 Git HEAD、工作区、暂存区和并发修改。
2. 不覆盖其他任务产生的修改。
3. 优先复用现有 `CookingControl`、`CookingDialog`、`CookingRecipeReader`、`CookingMenu` 和烹饪状态管理代码。
4. 不重写已经通过测试的烹饪识别能力。
5. 不修改采集、寻路、碰撞、地图和路线记忆。
6. 不直接写入游戏内存。
7. 不自动操作真实游戏。
8. 不部署 EXE。
9. 不推送 GitHub。
10. 每个阶段独立测试，阶段未通过不得进入下一阶段。

每阶段交付：

- 修改文件清单。
- 实现说明。
- 专项测试结果。
- 完整回归结果。
- 未解决问题。
- 下一阶段验收步骤。

## 十一、最终交付目标

完成后，用户只需要：

1. 自己走到灶台旁。
2. 设置需要制作的锅数。
3. 启动自动烹饪。

程序负责：

- 打开灶台。
- 使用默认食谱。
- 开始烹饪。
- 监测游戏随机翻锅事件。
- 根据实际事件翻锅。
- 自动收菜。
- 核对每锅产出。
- 自动开始下一锅。
- 达到目标数量后安全停止。

最终目标：玩家只负责选择灶台和启动任务，程序负责可靠地完成剩余烹饪流程。

## 十二、当前建议的执行决策

先执行 P0，不要一次性开发全部功能。

最重要的是在 P1 之前确认三件事：

1. 游戏内存是否能可靠识别随机翻锅事件。
2. 翻锅操作实际对应什么游戏原生输入。
3. 翻锅后能否通过状态变化确认操作成功。

这三个问题决定后续自动烹饪能否真正可靠运行。

项目开发原则：宁可暂停等待状态确认，也不允许盲目重复操作。

## 开发顺序建议

我建议把这份计划交给 Codex 后，严格按 P0 → P1 → P2 → P3 推进。

其中最值得投入精力的是 P1 的随机翻锅机制。它不是普通的定时任务，而是一个由游戏事件驱动、需要处理重复事件和延迟反馈的状态机。

最终验收不要只看能不能做出一锅，而要看能不能在不同随机翻锅次数下，连续、准确地完成三锅。

## 后续授权更新

用户明确取消原第十节关于不自动操作真实游戏、不部署 EXE、不推送 GitHub等本轮限制。现可按阶段操作真实游戏、接入入口、打包部署和提交推送；P0 → P1 → P2 → P3 的阶段验收要求继续有效。上述原文保留作历史方案，不再将已取消的执行限制作为阻塞理由。
