# M4-R1 底图接入实施记录

2026-11-24。基线 `8c68504`。配合 `M4-R1-reference-survey.md` 阅读，本文件只记录实施与验证。

## 决策与边界

采纳方式：**高清静态底图 + 本地缓存 + 独立动态标记图层**。

底图来自 TapTap 托管素材，无公开再分发许可，因此：

- 抓取、拼接、标定、校验代码入库；
- 底图本体 `runtime/basemap/basemap.png` 与标定 `runtime/basemap/basemap.json` **只存在于本地**，`/runtime/` 已写入 `.gitignore`；
- 打包 EXE 不包含底图；缺失时程序自动退回 M3 渲染，不报错。

## 关键实现

**只在视口变化时重绘。** `BaseMapLayer.draw` 以 `(x, z, scale, width, height)` 作签名，命中即返回，不做任何图像工作。实测 200 帧稳态下 `redraws=1`、`skipped=199`，直接证明「不得每帧重新生成完整地图底图」。

**金字塔分级。** 直接裁 4000px 原图再缩到画布，平移时每题约 57.9 ms。改为按当前缩放挑「刚好够用」的一级（4000/2000/1000/500 逐级折半，LRU 保留 3 级），裁切量下降约 8 倍。

**PhotoImage 复用。** 首版每帧新建 `ImageTk.PhotoImage`，Tk 图像往返开销明显；改为首次创建、之后 `paste` 原地更新。

**静态参照层让位。** 底图本身已画出水面、道路、木质平台。底图激活时，M3 的平涂地貌色块、水面填充、参考道路、木平台一律不画，否则会用不透明色块把美术细节压平。动态层（角色、轨迹、路线、资源、地皮）仍按原世界坐标叠加。

**失败可降级。** 缺缓存、图像损坏、PIL 不可用时，`available` 为假，程序回到 M3 渲染，不抛异常。

## 坐标标定

标定细节见 `M4-R1-reference-survey.md` 第 7 节。实施侧使用同一份 `basemap.json`，程序与工具共用 `WorldToImage`。

叠加校验（`alignment-check.png`）用世界水面轮廓、参考道路、木质平台逐项核对海岸线、湖泊、环状主路、草原湖、南侧平台，均吻合。

## 性能

实际 Tk 画布 760×560，同一套绘制函数。**注意：这不是完整应用窗口的测量**——实时窗口还有场景对象、符号、标签等来自游戏内存的绘制。

| 场景 | M3 | 底图 | 说明 |
| --- | --- | --- | --- |
| 稳态 中位 | 2.380 ms | **2.070 ms** | 底图反而更快：画布项从 93 降到 0，`finish()` 遍历更少 |
| 稳态 P95 | 3.121 ms | 2.818 ms | |
| 平移 中位 | 2.435 ms | 11.803 ms | 平移需重裁底图 |
| 平移 P95 | 3.170 ms | 12.772 ms | |

平移优化过程：57.9 ms → 14.4 ms（金字塔）→ 11.8 ms（PhotoImage 复用）。仍有 4.9 倍差距，属重采样固有成本；平移是用户主动操作，且程序已有 `interaction_pending` 延迟重绘机制。

## 测试

- `test_native_coordinate_monitor.py` 77 项全通过。
- 地形、水面、住宅图层等相关单测全通过。
- 全量结果见提交前的最终回归（`tests/test_architecture.py` 等 13 项为基线既有失败，与本次无关）。

期间修复两处自身引入的回归：

1. `base_map_enabled` 依赖构造顺序，部分测试装配的半成品窗口没有该属性，`draw` 抛 `AttributeError`。改为类级默认值 + `getattr` 兜底。
2. 底图与标定最初放在 `map/default/`，而 `map/<版本>/` 是随包地图库，4 个地图校验测试把它当作路线数据解析。缓存迁到 `runtime/basemap/`，与地图库隔离。
