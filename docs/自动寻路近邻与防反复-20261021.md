# 自动寻路：资源近邻与防反复

本轮依据矿石回放 `20261021-175956-755751-1cccf68f`（18:00:00—18:01:06）继续优化。该次从最近点接入第 8 点，记录 5 次受阻，未完成任何点。

## 资源中心不是人物落脚位

第 8 点坐标约 `(-131.38699, 19.08900, -70.01100)`，元数据明确是 `resource-center`，对应主地图矿石定义 436。最后三次卡住时，人物与中心的水平距离分别约 0.393、0.442、0.343，程序仍要求进入普通点位的 0.3 到达范围，因此继续追逐矿石中心并脱困。

停止后的实际只读场景确认：该坐标存在一个实时矿石实体，类别 ore、位置与配置中心一致。该确认说明实体存在，不代表已经检测到游戏中的 F 提示、当前可采集状态或材料掉落。

原 `ordered_waypoints()` 丢弃了 source 元数据，导致回放无法区分模型中心和手动记录的人物脚下位置。本轮保留深拷贝的 source；只有明确标注 `main-map-resource-definition`、`resource-center`、正确 ore/rock 编号和逻辑资源 ID 的点才启用近邻处理。

- 远处继续导航；进入 3 单位近邻后，核对唯一的实时同类实体，排除缓存、配置引用和歧义。
- 实体匹配后，在 0.75 单位以内、保持原高度容差的实际脚下站位收起移动，再执行原采集流程。0.75 是保守接近策略，不是从游戏读取到的最大交互半径。
- 需要继续接近时，在近邻环上选经过实体、水域和山壁检查的落脚位。连续受阻会改选位置，仍失败则按现有跳过/补采设置处理。
- 缺少实时实体时有限等待并记录原因，不因地图上的参考点而直接按 F。打开工具或食物面板后，会在按 F 前再次核对实体。
- 保存的路线文件不改写；循环仍使用原模型中心。手动记录的位置、普通路线高度检查和动态萤石/橡木流程保持原语义。

当前普通矿石没有接入可采次数或背包增量校验；这里确认的是实体与近邻站位，F 已发送与实际掉落仍是不同结论。

## 临时腿变化不再掩盖原地摆动

旧逻辑在导航临时腿改变时重置进展计时。路径若在两条等价走廊间反复变化，人物只移动几厘米也可能始终触发不了 2 秒卡住判断。

新增 `MotionProgress` 使用实际水平位移和回放活动时间，独立于当前临时腿。达到已有位移阈值才更新观察基点；校准、暂停、补给、受控等待、到点和脱困后重新开始观察。计算预算、丢失场景和用户暂停不会被当作物理卡住而触发跳跃。

受阻时不仅废弃局部路径，也清除旧大范围引导及其重试冷却；已记录的受阻探针仍保留。这样下一次规划不会继续复用经过刚才卡点的旧引导。

## 研究依据与边界

经用户指定代理检索 GitHub 并核对 [Navigation2 的 SimpleGoalChecker](https://github.com/ros-navigation/navigation2/blob/main/nav2_controller/plugins/simple_goal_checker.cpp) 和 [Unity Collider.ClosestPoint](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Collider.ClosestPoint.html)。前者将到达判定与路径规划分离，后者区分碰撞表面位置和任意给定点。本轮没有调用游戏 Collider 或 NavMesh API，也没有把配置中心自动投影成已验证地面。

没有加入直连回退，没有写游戏内存，没有启用已禁用的走法记忆，也没有用道路显示轮廓替代真实碰撞。

## 验证

`tests/unit/test_mineral_navigation.py` 使用上述三个真实卡点做替身回放，验证近邻采集不触发移动/校准/大跳；另覆盖最近点接入、缓存或歧义不按 F、跨楼层、循环保留原路线、工具检查期间实体消失、水域、临时腿反复改变时的原地卡住识别及旧引导失效。

本轮未自动在真实游戏中执行采集或完整路线；实际游戏操作仍由用户 F6 启动、F9 停止。完整导航网格、未读取到的碰撞和普通矿石实际掉落反馈仍有待补足。
