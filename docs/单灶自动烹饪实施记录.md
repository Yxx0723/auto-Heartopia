# 单灶自动烹饪实施记录

日期：2026-10-24

> 下文记录咖啡首版历史；当前默认食谱版本见文末更新。

## 本轮范围

根据《自动烹饪需求与实施方案》实施单灶首版。用户已明确忽略原文第十二条的“仅交付文档”限制，允许继续开发。首版支持已核对的咖啡，不宣称多灶、任意食谱或20锅连续验收已经完成。

## 已实现

- 独立单灶状态机，每锅从投料前开始保存作用域、首次库存、操作记录与唯一编号。收到稳定反馈前不会重复投料。
- 选菜时同时核对食谱标题、咖啡名称、四格咖啡豆和开始按钮；进入制作后区分计时标记、绿色锅铲、白色手套和灶台入口。
- 采用实际观察到的操作：Enter开锅，鼠标点击绿色锅铲，Q收菜；确认当前锅产出后才尝试重新打开选菜，交互无反馈有界停止。
- 翻炒提示只响应一次，只有再次明确观察到计时状态才重新允许翻炒；未知画面不能重置去重状态。操作前再次截图核对，允许少量图标位移，越界或失焦不点击。
- 每锅以咖啡的随身背包正增量确认。原料消耗只辅助记录，不要求每锅原料必须减少。锁定、高星、禁用同编号分堆整体保护，保留量每锅重新检查。
- 增加成功锅数、咖啡豆保留量、原料最高星级配置，以及本地重新标定入口。
- 通过共享输入锁保证烹饪与回放并发启动时也只有一个输入所有者；原有回放、维护、寻路和走法记忆配置不变。
- 任务线程执行识别、库存和输入，Tk线程仅显示状态。F6/F9、异常及窗口失焦会停止或暂停输入，退出释放输入、监听和只读句柄。
- 日志在独立“烹饪记录”目录按锅编号保存，事件与汇总去重；本地“烹饪配置”用于用户模板。两类目录均从版本控制排除。

## 源码与结构

- `utils/core/cooking.py`：食谱、观测、单灶状态转移和每锅证据。证据与小型状态机放在一起，避免为首版引入重复身份系统。
- `utils/flows/cooking.py`：可注入视觉、库存、输入和时钟的可中断流程。
- `utils/vision/cooking_menu.py`：选菜与材料核对，中央提示识别，多样本与歧义拒绝。灶台提示模板只保留归一化图标，排除人物背景。
- `utils/drivers/food_inventory.py`、`coordinate_memory.py`：复用原随身背包归属与稳定性校验，增加保守的烹饪库存读取。
- `utils/drivers/input_task_gate.py`：线程安全的共享输入所有权。
- `utils/ui/cooking_control.py`、`cooking_dialog.py`：任务生命周期、配置、标定和日志。
- `utils/ui/native_coordinate_monitor.py`、`point_playback.py`：窗口入口、状态显示和双向互斥。
- `tools/coordinate_monitor.py`：注入烹饪执行器，保持UI不反向依赖flows。
- `webui/coordinate-monitor/cooking-coffee.json`及打包spec：经采样的咖啡识别配置。

## 已取得的实机证据

用户手动完成两锅咖啡。只读TableBagitem名称核对咖啡为45108、咖啡豆为46106；游戏选菜界面显示四格咖啡豆。首次手动试做后的咖啡增加1、咖啡豆减少4；第二次咖啡再增加1，咖啡豆未进一步减少。因此不能以原料扣减作为产出确认的必要条件，也不能仅据此猜测第二锅免耗材的具体触发原因。

已采到选菜、计时、绿色锅铲、白色手套和收菜后入口的实际画面。绿色锅铲的输入方式由用户确认为鼠标点击。工具侧的人工UI输入未让开始按钮响应，前两锅均由用户操作，不能算程序自动烹饪通过。

## 离线与打包验证

- 先新增状态测试，旧代码因缺少烹饪模块无法收集；实现后验证延迟开始、翻炒去重、延迟入包、缺失基准、作用域隔离、材料保留、超时、重新开菜单、输入清理与互斥。
- 完整默认测试：2378通过、27原有预期失败、0失败/错误，另2个子测试通过，耗时152.43秒。
- 冻结包测试：809通过；89个项目源码模块与包内代码一致；咖啡识别JSON也与源文件一致。
- 已采样真实画面的离线识别覆盖两种镜头下的计时/收菜以及第二次的翻炒提示；这是已录画面验证，不等于完整自动烹饪实测。
- 当前机器、并行测试环境中，5次已录画面识别：选菜中位约6.8ms，翻炒中位约122ms。没有将其当成真实响应期限或端到端输入延迟。
- 300秒任务/识别等待、15秒收取及重新打开菜单等待、0.1秒轮询、0.5秒库存轮询、4像素目标位移容差均为工程预算，不是游戏实测能力值；集中在thresholds并登记测试。

## 能力边界与后续验证

1. 当前仅核对咖啡；其他食谱、替代材料、万能食材、仓库与多灶未开放。
2. 没有可依赖的烹饪内部阶段字段，当前使用画面与背包核对。原料星级和锁定状态来自已有只读结构。
3. 不保证成品星级。未知产物或未核对的失败产物不会被当成目标成功；首版可能保留为待确认并停止。
4. 当前样本不是所有灶台、镜头、分辨率及UI比例的覆盖保证。模板不符时要恢复条件或重新标定，不能放宽到任意连点。
5. 首版不在锅内过程插入自动进食、维修或装备操作。低体力等额外游戏行为仍需另行实机核对。
6. 连续20锅、分辨率变化、背包满和断线恢复仍需要后续受控实机验收，不能由离线测试代替。
7. 多灶需要独立灶台绑定及可靠操作期限，保持为后续阶段，不由首版自动启用。

程序自动单锅的运行结果在实际验收后补充；不得将上述手动采样改称自动完成。


## 默认食谱简化（2026-10-24）

用户取消自动选择食谱：仅使用灶台默认选择及游戏已填材料，不做食谱列表、搜索或自动替料。去除咖啡限定与人工勾选项；点击开始尝试激活绑定游戏并运行，激活失败才要求F6。

新增只读`cooking_recipe.py`，沿CookingSystem泛型单例→当前场景Owner→`_recipeDetail`→MaterialSlot引用数组读取。校验运行域、类型、字段布局、前后场景/单例/引用/字节内容。只读缓存详情不代表菜单已打开，必须同时有稳定可用的选菜开始按钮才授权投料。作用域绑定当前场景模块，不提供独立灶台网络身份。

复用原背包归属读取，增加netId与可用分堆总数。核心状态机逐个核对当前填入分堆的归属、锁定、星级、重复使用份数及保留量。操作前再次读取菜单签名与背包；菜单变化、材料临时锁定或场景改变不能输入Enter。锅内仍以视觉状态驱动，每锅收取后核对料理类型45实际增量，允许不同默认填料形成变体，不假设产物一定是咖啡。相同时间其他来源的料理增量仍有归因歧义。

当前实机只读核对：默认食谱45108咖啡，四槽均为46106咖啡豆，归属相同背包分堆；首次读取约78ms（包含类目录冷初始化）。没有发送输入，没有新自动单锅验收；此前两锅仍为用户手动采样。槽位上限8为工程边界，非游戏能力实测值。

回归和冻结包验证记录在本次交付制品目录；其他料理/多锅、自动激活、打开默认菜单、翻炒及成品归因需要后续受控实机核验。

本轮实际验证：烹饪专项66项；完整默认回归2403通过、27原有预期失败、0失败/错误，另2子测试通过（167.25秒）。pyflakes、compileall、架构契约与差异检查通过。最终冻结包834项通过，90模块与源码一致。并行复验曾有1项原地图测试遇到Tcl init.tcl读取失败，保留失败日志后单独重跑全部冻结专项通过；未因此修改地图业务逻辑。完整回归使用相对JUnit路径，测试临时工作目录清理后XML未保留，结果以保存的full.log为准。
